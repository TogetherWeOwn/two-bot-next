# Container logging contract

The gateway/server process writes one JSON object per stdout line by default,
including a boot without `DISCORD_TOKEN`. There is no nested `fields` envelope.
Docker explicitly sets `LOG_FORMAT=json`; native runs also default to JSON.

## Configuration

- `LOG_FORMAT=json|pretty`: `pretty` opts into tracing's human-readable formatter.
  Missing/unknown values use JSON. Unknown values emit `log_format_invalid`
  without echoing the value (subject to the level filter).
- `RUST_LOG`: valid, nonempty tracing EnvFilter directives take precedence, e.g.
  `warn,two_bot=debug,two_bot_discord=info`. Malformed/empty directives fall back
  to `LOG_LEVEL` without plain-text stderr diagnostics.
- `LOG_LEVEL`: `trace`, `debug`, `info`, `warn`, `error`, `off` (case-insensitive).
  Missing/invalid levels default to `info`. The level applies to the `two_bot`
  target prefix (all workspace crates); anything else logs at ERROR only
  unless `RUST_LOG` opts in. `/readyz` 503s log at DEBUG, not ERROR.
- `--help`, backup/export CLI stdout, and the silent `--healthcheck` probe are
  separate protocols, not JSON logging. Panics/OS diagnostics are not tracing
  events and are not covered by this format contract.

## Fields

| Field | Convention |
| --- | --- |
| `ts` | UTC RFC3339 timestamp generated by tracing's `SystemTime` formatter |
| `level` | Lowercase `trace`, `debug`, `info`, `warn`, `error` |
| `msg` | Stable lowercase snake_case event name; never interpolate IDs/errors |
| `target` | Rust module/explicit tracing target, useful for filtering |
| `message` | Optional human explanation; not an alert key |
| `guild_id`, `interaction_id` | Discord snowflakes as decimal **strings**, not JSON numbers |
| `run_id` | Process invocation correlation: boot Unix nanoseconds + PID; not a durable job/session ID |
| `spans` | Root-to-leaf list of named spans and typed fields; omitted when no span applies |
| `code`, `count`, `hot_keys`, `revision` | Numeric bounded status/counters/revisions |
| `signal`, `missing`, `reason` | Short bounded classifications/binding names, not raw provider data |

Event fields are flattened into the root. Correlation fields from spans are also
promoted to the root: inner span wins over outer; explicit event field wins over
spans. `ts`, `level`, `msg`, `target`, and `spans` are reserved envelope keys.
The server future is instrumented with a run span; the spawned gateway task adds
a guild span. The synchronous interaction route adapter adds interaction/guild
spans. Futures use `Instrument`, not an entered guard held over an `.await`.
New tasks must propagate context explicitly; synchronous span context is not
implicitly inherited by `tokio::spawn`. Axum spawns the graceful-shutdown signal
future internally, so that future explicitly carries the run span and subscriber
as well; `shutdown_started` keeps the same `run_id` as boot and drain completion.
Run/guild/interaction correlation spans remain enabled independently of event
verbosity, including `WARN`, `ERROR`, and `OFF`; `OFF` still emits no events.
HTTP request execution restores the serving future's run span and subscriber
around the trace layer, including Axum's separately spawned connection tasks.
HTTP request spans record the method and a redacted path only (no query string
or headers; any `webhooks` path is fully redacted) and remain available for failure
logs.

Existing snake_case message-only events retain their name as `msg`. Events with
neither a valid string `msg` nor a snake_case `message` use `msg=tracing_event`,
retaining the human `message`. This keeps third-party tracing output parseable
without treating free-form messages as an event-name contract. New application
events should specify `msg` explicitly:

```rust
tracing::info!(msg = "job_started", job = "scorecard", "starting weekly job");
```

Example (field ordering is not a contract):

```json
{"ts":"2026-09-30T12:00:00.000000Z","level":"info","msg":"ready","target":"two_bot::gateway","guild_id":"1545644954272137297","run_id":"1790769600000000000-1","spans":[{"name":"run","run_id":"1790769600000000000-1"},{"name":"gateway","guild_id":"1545644954272137297"}]}
```

## Lifecycle event catalog

Names below are stable. Add names rather than renaming existing ones. `ready`
and `gateway_resumed` are emitted only after successful durable dispatch commit
with a fresh generation, not merely receipt of a Discord packet. A token-free
boot parks the gateway; `http_listening` is **not** proof of Discord readiness.
Reception ends cooperatively through the drain, not a stream-end event; the
draining state is observable via `/readyz` and `shutdown_started/completed`.

| `msg` | Emission point / fields |
| --- | --- |
| `config_invalid` | Invalid runtime config; safe, value-free config error |
| `log_format_invalid` | Unsupported format; falls back to JSON |
| `gateway_parked` | Missing prerequisite; `missing`, `status` |
| `gateway_connecting` | Durable store loaded, before connecting; `resume` |
| `gateway_started` | Gateway loop begins; `shard` |
| `ready` | READY processed and checkpoint committed; `shard` |
| `gateway_resumed` | RESUMED processed and checkpoint committed; `shard` |
| `shard_closed` | Gateway close received; optional `code`, no close reason/session |
| `gateway_reconnect_failed` | Twilight reconnect failed; retry remains Twilight-owned |
| `gateway_failed` | Durable gateway task failed; no SQL/task error or URL |
| `http_listening` | Listener bound; `addr` (bind address only) |
| `settings_applied` | Hot-setting refresh report logged; `revision`, `hot_keys` |
| `settings_reloaded` | Preserved legacy refresh event; revisions and row counts |
| `setting_changed` | Preserved hot-key event; `key`, `guild_id`, `from`, `to` |
| `setting_stored_needs_restart` | Cold key stored; `key`, `guild_id` |
| `setting_ignored_not_applied` | Env-only/unknown row ignored; `key`, `guild_id`, `reason` |
| `shutdown_started` | Signal received; `signal=SIGTERM|SIGINT`, before HTTP drain |
| `shutdown_completed` | HTTP graceful drain completed successfully |
| `shutdown_failed` | Service/supervisor failed; process exits nonzero |
| `tracing_event` | Uncataloged/free-form tracing diagnostic; inspect `target`/`message` |

### Reserved job names

These names are reserved, not a claim that all ~208 legacy feature messages are
ported. The entrypoint now runs the website-job supervisor; its existing
free-form diagnostics use `tracing_event`. This logging slice does not rename
those diagnostics or wire additional schedulers/settings polling. `settings_*`
emit when the existing refresh-report hook is invoked. Future job call sites
should use these names when adding explicit lifecycle instrumentation:

| Reserved `msg` | Required conventions |
| --- | --- |
| `job_started` | `job`, `run_id`, optional `guild_id`; actual execution begins |
| `job_completed` | Same correlation plus `duration_ms`, optional `count`; successful completion only |
| `job_failed` | Same correlation plus bounded `reason`; never raw SQL/HTTP error |
| `job_skipped` | `job`, bounded `reason` (`disabled`, `busy`, `not_due`); not a completion |

## Redaction rule

**Never log tokens or URLs containing credentials.** Also exclude authorization
headers, interaction callback paths/tokens, database DSNs, S3 signed URLs/keys,
gateway session IDs/resume URLs, raw packets, request bodies, message contents,
modal/component values, and debug dumps of config/interactions/requests. Prefer
binding names, allowlisted identifiers, counts, status codes, and bounded reasons.
Do not add `%error`/`?error` for SQL/HTTP/provider failures: their display/debug
chains can contain URLs. HTTP tracing records only the method and a redacted path. Existing settings
reports log only catalog-approved hot-key values; never add env-only/secret values
to those reports. Database URL query keys are validated before SQLx parses them:
unsupported keys (including `sslpassword`) are rejected without logging keys or
values. Parse-scoped passfile diagnostics are suppressed by the existing core
`database_url` helper; do not bypass that helper with direct SQLx URL parsing.

The JSON formatter is an encoder, **not a general secret scrubber**. Call sites
must select safe fields before emission. Global third-party debug/trace can expose
provider internals; use targeted `RUST_LOG` directives and inspect output before
raising verbosity in a managed container. JSON escaping prevents multiline data
from becoming multiple log lines, but does not redact it.

## Verification

- `cargo test -p two-bot --bin two-bot logging:: --locked`: captures every line,
  checks string envelope/flat typed fields, escaping, spans/record updates,
  filter precedence, reserved key safety, pretty opt-in, and URI omission.
  Regressions cover WARN/ERROR/OFF correlation, synthetic rejected-DSN diagnostics
  (no database connection), graceful shutdown, and actual TCP `/health` +
  `/readyz` request/failure correlation under DEBUG/WARN/ERROR.
  On the controller, use the bounded wrapper in [build-cache.md](build-cache.md).
- Hosted `container smoke` job (`check.yml`, gated on image inputs): reuses the
  image it builds from the repository Dockerfile with locked dependencies, runs
  it without token/database/guild bindings, probes local health, sends SIGTERM,
  then parses **every** combined stdout/stderr line. Asserts `gateway_parked`, `http_listening`,
  `shutdown_started`, `shutdown_completed`; no Discord/database request occurs.
- Smoke runner: `python3 scripts/test-logging-container.py IMAGE`. It creates a
  local isolated `--network none` container, never connects to staging/production,
  and removes only its own container in `finally`.

## Implementation sources

- [tracing-subscriber 0.3.23 FormatEvent](https://docs.rs/tracing-subscriber/0.3.23/tracing_subscriber/fmt/trait.FormatEvent.html#examples): custom event envelope and `FormattedFields` span access.
- [JSON/JsonFields](https://docs.rs/tracing-subscriber/0.3.23/tracing_subscriber/fmt/format/struct.Json.html): feature-gated typed JSON field formatting.
- [EnvFilter](https://docs.rs/tracing-subscriber/0.3.23/tracing_subscriber/filter/struct.EnvFilter.html#constructing-envfilters): strict directive parsing.
- [Instrument](https://docs.rs/tracing/0.1.44/tracing/trait.Instrument.html#method.instrument): enter spans on future polling, propagate context into spawned work.
