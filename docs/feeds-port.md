# Feeds port: domain and store contract

This is the self-contained TOG-10085 domain/store slice. It does **not** activate
feeds or implement a second interaction dispatcher, Discord client or HTTP client.
Runtime wiring stays on TOG-10085 after the shared interaction router (TOG-10075)
and REST executor (TOG-10076) land. No production guild or token was used.

## Legacy behavior retained

Read-only specification: TogetherWeOwn/two-bot `src/announcements/service.ts`,
`store.ts`, `discord.ts`, `feedHttp.ts`, and migrations `0024`/`0025`.

- `/feed-add`, `/feed-remove`, `/feed-list` shapes already live in
  `feature_commands.rs`; commands are guild-only, require ManageGuild, and use
  the invoking channel. `plan_command` also verifies enabled/configured guild
  and permissions at execution time. IDs are generated by the adapter.
- RSS and Twitch sources are HTTPS XML feed URLs. Twitch is **not** a Helix API
  integration and does not require a Twitch credential. YouTube also accepts a
  20–32-character channel ID and expands it into the videos Atom URL.
- RSS item/guid and Atom entry/id parsing, alternate-link preference, title,
  published/pubDate/updated fields, 200-item ceiling. No external entity resolver;
  DTD disabled, XML node count bounded. An iterative, allocation-free preflight
  rejects depth above 64 (including self-closing elements), more than 64
  attributes on one element, or more than 4,096 attributes in the document
  **before** roxmltree constructs it. Namespace declarations count as attributes;
  comments, CDATA and processing instructions are opaque. These limits protect
  synchronous parser stack/CPU independently of the byte/node/item ceilings,
  which an async deadline alone cannot do. UTF-8 fixtures cover all three kinds.
  Container attributes shadow child fields; repeated RSS channels are not a
  single channel record, while repeated items/entries remain supported.
- Exact User-Agent: `Owen/1.0 (+https://two.gg)`. Decompressed byte ceiling:
  `2_000_000`. Per-feed deadline: 15 seconds, across DNS/redirects/body parsing.
- `TWO_ANNOUNCEMENTS` stays default-off. Existing `FeatureGates` reads
  `TWO_FEED_POLL_SECONDS`, default 300, range 60–86400. `FeedPollSchedule`
  permits an immediate first pass and suppresses overlapping passes.
- Oldest-first candidate order, per-item isolation, at most 20 new posts per feed
  per pass. Apply the cap **after** checking claims; delivered rows must not
  consume the cap or hide the unseen tail. Deferred, never-sent claims release
  for the next pass. Replies/posts cap UTF-16 length at Discord's 2000 units.
- SHA-256 item-key fallback and 24-hex nonce are byte-compatible with legacy.
  Posts require empty allowed_mentions and enforce_nonce.
- Migration `0180_feeds.sql` preserves `feed_relays` and `feed_deliveries` column
  names/types, uniqueness/cascade, and legacy claim columns. It coexists with
  `0160_rsvp`'s shared `announcements_audit_log`. Adapter writes create/remove,
  item-failure, poll-result and deferred-count audits via `write_audit`.

## Required transport enforcement

`feeds_http` is the pure policy; `feeds_connector` is the transport that consumes
it. `fetch_feed`/`fetch_feed_with` enforce the full contract:

1. Normalize/validate the source, resolve **all** A/AAAA answers per request,
   and create a `PublicRequest`. Empty or mixed-public/private results fail closed.
2. Dial **only `PublicRequest::addresses()`**, retaining the original hostname
   for certificate verification/SNI and Host. `PinnedResolver` answers hyper's
   connector for exactly the pinned host and refuses every other name; a fresh
   `Client` per request means no pooling, no proxies and no second DNS lookup.
   IPv4-special networks, mapped/compatible IPv6, NAT64, ULA, link-local and
   non-global IPv6 are refused at `PublicRequest::prepare`.
3. Automatic redirects are off. Only 301/302/303/307/308, same-host HTTPS targets,
   at most three hops, each hop re-resolved and re-pinned before dialling.
   No credentials, cross-host moves or downgrades.
4. Content type and advertised length are checked, the compressed wire read is
   capped at `MAX_FEED_BYTES`, and decompressed output is capped again before
   `LimitedBody` and the UTF-8 check — a zip bomb dies in the stream, not the
   parser. One total 15-second deadline (`FetchOptions::default`) covers DNS,
   every hop and the body read.
5. The injected `FeedResolver`/`FeedConnector` seams prove the orchestration
   without opening sockets: pinned dials, all-answer validation, rebinding,
   cross-host/downgrade/credential redirects, the three-hop budget, the single
   deadline, wire/decompressed caps, encoding refusal and fixture parity. The
   private-fixture bypass (`PinnedResolver::for_test`) exists only under
   `#[cfg(test)]`.

## Delivery state and crash boundary

`claim_delivery` acquires a unique `(feed_id,item_key)` claim with an
adapter-generated, never-reused owner token. Concurrent workers have one winner.
Only pending leases older than 60 seconds can be reclaimed; completion/release
is token-fenced and guild-scoped. Delivered rows remain final across restarts.

- **Fresh:** Send with the stable nonce; on confirmed message ID, mark delivered.
- **Fresh over budget:** release without sending and defer.
- **Expired/recovered:** reconcile by nonce; if the existing message is found,
  mark delivered with the new owner token. Never immediately repost.
- **Ambiguous send, post-success DB error, missing bounded-history match:** leave
  pending and report recovery required. Do not call `release_unposted`.

This deliberately tightens the legacy blind expired-claim retry. Discord only
provides a short-lived nonce deduplication window, not an indefinitely durable
idempotency key. A DB claim and an external message send cannot be atomically
committed. **Exactly-once eventual delivery across arbitrary crashes is not
proved here**: confirmed deliveries are deduplicated indefinitely; the
post-accepted/pre-DB crash test recovers one mock message without reposting;
unknown acceptance remains pending rather than risking duplicates or claiming
success. The shared executor must implement reconciliation and surface unresolved
claims; missing in a bounded 100-message search is not authoritative absence.

## Verification

```sh
cargo fmt --all -- --check
cargo clippy -p two-bot-core --all-targets --all-features --locked -- -D warnings
cargo test -p two-bot-core --test feeds --locked
cargo test -p two-bot-core --test feeds_connector --locked
TWO_TEST_DATABASE_URL=postgres://agent_test@agent-testdb:5432/agent_test \
  cargo test -p two-bot-core --features db --test feeds_store --locked -- --ignored
```

DB tests refuse other hosts/users/databases/ports **before connecting**, use only
unique owned schemas, and drop only those schemas. Ignored by default; the
`feeds db check` CI job explicitly executes them against its disposable Postgres
service. No DATABASE_URL fallback, production/staging connection or credentials.
They cover migration coexistence/re-execution, CRUD/guild fencing, timestamp
round-trip, 16 simultaneous claimants, lease expiry/stale-owner fencing, reopened
pools, mocked Discord crash reconciliation, and 20+5 overflow across two passes.

Remaining on the runtime slice: register shared-router handlers, consume these
plans through the shared REST executor, wire `fetch_feed` into the poll adapter
behind its delivery-store orchestration, start/stop the poll timer, attach
bounded audit/failure recovery, and run the connector/mock-Discord end-to-end
acceptance tests. Keep activation default-off.
